# Bugs for the next Rivet update

Found by kaiser on his phone, Rivet 1.0.0, 1 Nov 2026. Decision (kaiser, 1 Nov): note them all, fix together in the next update — no hotfix now.

## 1. Run hangs mid-reply, no error, app thinks it's still generating
- What happens: on a big build task ("create a single-file Three.js Minecraft clone", DeepSeek V4.1 Flash 1017, empty workspace "3d"), Rivet inspected the workspace, created the empty file, then its next message cut off mid-word — "The file is created but still empty; let" — and nothing ever happened again. No file write, no error, composer kept showing the stop (generating) button.
- Evidence: `bug-2026-11-01-stuck-stream.jpg` (this folder).
- Suspect area: streaming/agent loop — a provider stream that stalls or ends without a finish signal, and no stall watchdog to surface it. Token-limit cut (finish_reason=length) with no recovery is the other candidate.
- Status: DIAGNOSED 1 Nov 2026 (Rivet dsh session, static read of the sources — no build/run). Verdict:
  - **Root cause:** the SSE stream reader in `Http.kt::sse` (~lines 216-277) has no progress or idle deadline. Its only bound is a 300s per-read socket timeout, and heartbeat bytes reset that bound forever. Every truncation detector (`IncompleteGeneration`, `InvalidResponse`, incomplete-stream) only fires when the stream ENDS — so a stream that never ends (terminal `finish_reason`/`[DONE]` chunk never arrives, socket stays open) produces exactly this: frozen bubble, stop button, no error, forever.
  - **Likely trigger:** the model hit its output ceiling mid-token on the huge single-file game (`finish_reason=length` would have shown "The model stopped before finishing its response" — the fact that NO error appeared is itself evidence the terminal chunk never arrived).
  - Ruled out: the agent loop (a text-only turn ends the loop immediately, `AgentLoop.kt:176-186`) and UI state handling (all paths clear `streaming`; the Stop button would have recovered it).
  - **Smallest fix (one file, `Http.kt::sse`, no signature/UI changes):** track `lastProgressAt`, refreshed only when a real `data:` payload is delivered (not heartbeats); after each line read, if no progress for ~120s, throw `ProviderError.Timeout` — that error already exists, already renders ("The provider took too long to respond"), already clears streaming and keeps the partial text with retry. Optionally build the streaming call with a matching read timeout so a fully silent socket trips in ~2 min instead of 5.
  - Companion fix (separate, don't bundle blindly): accept a stream that delivered a terminal `finish_reason` but omitted `[DONE]` instead of throwing `InvalidResponse("incomplete stream")` (`OpenAiCompatibleClient.kt:98` + a `sawFinish` flag on the stream parser).
  - Open question for kaiser if he remembers: was it still stuck after ~5-6 minutes, and was the app backgrounded during the run (bug #2 makes the half-open-socket path more likely)? The fix is the same either way; it only tunes the stall limit.
  - Follow-up (kaiser, 1 Nov ~09:55): the stuck run DID eventually respond after a long stall — consistent with the diagnosis (a long silent stretch finally ended or tripped the 300s read bound). Kaiser notes his provider generates at ~120 tokens/s — true, and not in conflict: generation speed is not stream delivery; the failure is the missing terminal chunk plus Rivet having no progress deadline. The app-side fault stands regardless of which side dropped the chunk.

## 2. Switching to another app kills the run with a network error
- What happens: if the user leaves Rivet mid-run (switches apps), the run dies with a network error instead of continuing.
- Suspect area: no foreground service / keep-alive for an active run, so Android suspends the process or the socket is dropped when backgrounded; the stream reader treats the drop as a fatal network error instead of resuming or retrying.
- Fix direction (to confirm at build time): foreground service while a run is active + treat a dropped stream as resumable, or at minimum fail soft with a "resume" instead of a dead run.

## 3. No way to see whether the agent is writing or stuck
- What happens: during long work (e.g. writing a big file) the UI gives no live signal of what is happening — no streaming file content, no per-tool progress, no heartbeat. A healthy long write and bug #1's hang look identical from the user's seat.
- Fix direction (to confirm at build time): live activity feedback during tool work — show the current action and stream file content/progress as it is written, plus a visible "still working" heartbeat tied to real stream/tool events.
- Kaiser's explicit ask (1 Nov): stream like the ChatGPT / Claude apps — a visible thinking state while the model is thinking (before and between text), then the reply appearing word by word as it is generated, so "thinking" and "stuck" are never the same picture. Where a provider sends reasoning deltas, show the thinking live; where it doesn't, the working indicator plus word-by-word text still carries the signal.
- Design reference (kaiser, 1 Nov, screenshot of his dsh agent-team chat running the repo audit): "dsh chat looks so alive." What makes it feel alive, to copy the feel (not the skin): every step visible as it happens (Skill / Bash / Think rows with live status), the thinking shown as its own block, and a running elapsed-work line ("Deep diving for 38s…") that keeps ticking while the model works — the user can always see WHAT is happening and HOW LONG it has been happening. That elapsed ticking line is the cheapest anti-"is it stuck?" signal there is. Kaiser's words: "We need this type in Rivet so we know in app what's happening and if AI is working."
- Diagnosis tie-in (1 Nov): `ChatScreen.kt:636` suppresses the activity row whenever `streamingText` is non-blank — so during exactly the long writes that matter, the progress row hides. Flipping that condition, or adding a stall-driven "still working…" state when no delta has arrived for N seconds, makes a healthy long write visibly different from bug #1's hang.

## 4. "The provider sent more data than Rivet can safely process" — Rivet's own 1 MB cap kills big-file work
- What happens (kaiser, 1 Nov ~09:55, same "3d" project, minimax-m3.1-flash): the model wrote the full game in one go (Edited 1 file, OK), then a fix-up edit failed ("patch didn't match"), it re-read the whole file twice, and on "continue" the run died with the red banner: "The provider sent more data than Rivet can safely process. Try again or choose another model." Evidence: `bug-2026-11-01-response-too-large.jpg` (this folder).
- What it actually is: Rivet's own safety limit, not a provider fault — `Http.kt:47` caps a streamed response at `MAX_SSE_RESPONSE_BYTES = 1 MB` total (also 128 KB per single line, `Http.kt:46`); crossing it throws `ProviderError.ResponseTooLarge` (`Http.kt:248`), rendered by `ProviderError.kt:46`. A full game file sent back as edit/tool arguments crosses 1 MB easily.
- Why it's a real bug, not just a limit: (a) 1 MB is too low for Rivet's core job — writing big files in one go; (b) the recovery is a dead end — "choose another model" changes nothing, every model trips the same cap; (c) the copy blames the provider for Rivet's own limit.
- Fix direction (to confirm at build time): process the stream incrementally instead of hard-killing at a total cap (or raise the cap a lot and keep a per-line sanity bound), support chunked writes for very large files, and make hitting the limit recoverable (auto-continue the generation) instead of a dead banner. Fix the copy to say what actually happened.
- Also observed in the same run (context, not yet a filed bug): exact-match patch edits fail on large self-written files ("The patch didn't match"), causing re-read loops that balloon the payload — which is part of what pushed the next response over the cap.

## 5. Downloaded Linux binaries can't run in the command sandbox — and the agent keeps retrying anyway
- What happens (kaiser, 1 Nov ~09:58, same "3d" project, DeepSeek V4.1 Flash 1017): after cleanly rewriting the game file, the model went on a self-assigned side-quest — fetch three.js locally, validate the JS with Node. No Node on the device → it downloaded the Node .tar.xz (failed, no xz) → downloaded the .tar.gz build → extracted it → ran `./node-v20.18.0-linux-arm64/bin/node -v` → **Exit 126** (found but not executable: a glibc Linux binary cannot execute inside Android's app sandbox). Every step failed; the model kept escalating fetch strategies instead of recognising the wall. Evidence: `bug-2026-11-01-save-changes-failed.jpg`.
- Two faults: (a) the runtime never tells the model its limits — no note that downloaded/system binaries can't execute and big downloads are off the table, so models burn turns and the user's data on doomed setups; (b) the fetch adventure polluted the project with `.rivet-test/` junk (tarballs + a full extracted Node tree) the user never asked for. Also note the original ask — "launch it in localhost so I can play" — never happened; the side-quest ate the task.
- Fix direction: a runtime-limits note in the agent's environment briefing (what the sandbox can and cannot do: no external binaries, no package/runtime downloads, size expectations), plus a command-layer guard that warns/blocks on huge downloads into the project.

## 6. Saving a command's project changes fails on the mess the command made (sync_failed)
- What happens (same run, immediately after bug #5's cascade): red banner — "Rivet couldn't finish saving the command's project changes. Some files may already be saved; Rivet kept the pending changes." (Discard pending changes / Try again / Dismiss.)
- What it actually is: commands run against a mirror of the project; afterwards Rivet syncs the mirror back to the real folder. This is the `sync_failed` path (`ChatViewModel.kt:123`, runtime failure mapping) — the sync died partway walking the tree the commands created: a full extracted Node distribution (thousands of files, symlinks, binaries) is exactly the kind of tree the syncer can't safely copy (there is a separate `unsafe_entry` stop for items it can't safely access). The safety behaviour itself is right — it kept the pending copy and overwrote nothing — but one bad subtree fails the WHOLE sync and strands the project in a pending-changes state.
- User impact in this case was low (the game file itself had already been saved by the normal edit path; the unsynced changes were the Node junk) — but on a real project the same failure could strand work the user actually wants.
- Fix direction: make the sync fault-tolerant per entry — skip/report unsafe or oversized entries instead of failing the whole sync; exclude tool/cache directories (`.rivet-test`, tarballs, extracted runtimes) from syncing by default; if a sync does fail, say WHICH items failed in plain words.

## Note
Bugs 1 and 3 are cousins: part of the fix for both is the same visible heartbeat — the UI should always be able to answer "is it writing right now, yes or no."
Bugs 5 and 6 are also one story: an agent that doesn't know its sandbox limits creates trees the syncer can't save. Kaiser found this whole cluster in ONE real session on his own phone — this is the dogfooding pass no emulator test produced. His words on the session: "we need to fix a lot ngl... now i know after using it myself." The next update is a stability update.
