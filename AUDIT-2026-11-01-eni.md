# Rivet — Stability Audit

**Repository:** [Kaiser0733/rivet](https://github.com/Kaiser0733/rivet)
**Audited commit:** `c0c49c83a715e03378077938c3a43464a397ef4a` (2026-10-28, merge of #37)
**Scope:** whole repository, read-only. 16,034 lines of Kotlin in `app/src/main`, plus the `terminal-emulator` JNI sources.
**Method:** clean clone, full call-path tracing from UI → ViewModel → agent loop → provider client → HTTP/SSE reader → JNI. Every claim below points at code I opened. No files in the repo were modified, no build was run, nothing was executed on a device.
**Not verified:** anything requiring a real provider, a real phone, a network switch, or a process kill. Those are marked POTENTIAL with the exact experiment that would confirm them.

Severity is the user's experience, not the code's elegance: `data-loss` > `hang` > `crash` > `wrong-result` > `annoyance`. A `crash` that loses nothing outranks a `wrong-result` that makes a turn useless, so severity alone is not the ranking — see the Top 10.

---

## 1. Provider streaming

Every provider client shares one SSE reader (`Http.kt`) with two exceptions: `ChatGptPlanClient` has its own copy of it (`responsesSse`), and each client has its own truncation detector. The four detectors do not agree with each other, and that is where most of this section comes from.

### F01 — A stream that keeps sending heartbeats hangs the reply forever
- **Severity:** hang
- **Status:** CONFIRMED
- **Evidence:** `provider/Http.kt:28` (`readTimeout(300, SECONDS) // SSE streams idle between deltas`), `Http.kt:238-261` (the read loop), `Http.kt:257` (`if (!terminal.get() && payload.isNotEmpty()) onEvent(payload)`). No overall deadline exists anywhere; the only guard is the socket's *idle* timeout.
- **Trigger:** a provider or proxy that stays connected and keeps sending SSE comment lines (`: ping`) or empty `data:` payloads, which is exactly what several OpenRouter upstreams and mobile-network carrier proxies do to hold a stream open. Each of those lines is consumed by the loop and resets OkHttp's idle timer, but produces no delta because `payload.isEmpty()` skips `onEvent`. A dead-but-not-closed TCP connection behind a heartbeat is indistinguishable from a live one.
- **What the user sees:** the assistant bubble stops mid-word with the blinking streaming state still on. No error, no timeout, no way to tell it is dead except tapping Stop. It can stay there indefinitely. This is the confirmed mechanism behind the reported "hangs forever mid-word".
- **Fix shape:** add a progress deadline in the read loop — track the timestamp of the last *delta* and abort with `ProviderError.Timeout` when the gap exceeds a fixed budget, independent of any byte that arrives.

### F02 — A provider that never sends `[DONE]` throws away a complete answer, and every truncation is reported as a parse error
- **Severity:** data-loss
- **Status:** CONFIRMED
- **Evidence:** `Http.kt:253-256` sets `completed = true` only on the literal string `[DONE]`. `OpenAiCompatibleClient.kt:98` (`if (!completed) throw ProviderError.InvalidResponse("incomplete stream")`). `ProviderError.kt:44` maps that to *"The provider returned a response Rivet could not parse."* The same flattening happens in all three other clients: `AnthropicClient.kt:269`, `GeminiClient.kt:204`, `ChatGptPlanClient.kt:213` — each throws `InvalidResponse("incomplete stream")`.
- **Trigger:** two distinct conditions collapse into one failure. (a) An OpenAI-compatible endpoint or proxy that closes the stream after the final chunk instead of writing `data: [DONE]` — the model finished cleanly, `finish_reason` was `"stop"`, and the full text is sitting in `OpenAiAgentStream.text`. (b) A genuine mid-stream drop. In both cases the accumulated text is discarded with the accumulator object and the user is told the *response could not be parsed*, when in fact it was parsed perfectly.
- **What the user sees:** the answer streams in completely, then vanishes, replaced by "The provider returned a response Rivet could not parse." Re-sending produces the same thing if (a) is the cause. The user concludes Rivet is broken with their provider; the provider is fine.
- **Fix shape:** accept the response when a finish signal was observed and text/tool calls exist, treating a missing sentinel as a clean EOF; give truncation its own error (`IncompleteGeneration`), not `InvalidResponse`.

### F03 — Rivet's own 1 MiB cap kills big-file work and blames the provider
- **Severity:** data-loss
- **Status:** CONFIRMED (this verifies known bug #4)
- **Evidence:** `Http.kt:47` (`MAX_SSE_RESPONSE_BYTES = 1024 * 1024`), `Http.kt:247-250` (`responseBytes += line.toByteArray(...).size + 2; if (responseBytes > MAX_SSE_RESPONSE_BYTES) throw ProviderError.ResponseTooLarge()`). Message at `ProviderError.kt:46`. The identical cap and message live in the Responses-API copy at `ChatGptPlanClient.kt:273-276`.
- **Trigger:** any single reply whose SSE bytes exceed 1 MiB. Because the counter sums wire bytes (including JSON escaping, `data:` prefixes and keepalives), the usable payload is smaller than 1 MiB — roughly 300–500 KB of file text. One `write_file` of a 2,000-line source file, a lockfile, or a generated bundle crosses it.
- **What the user sees:** *"The provider sent more data than Rivet can safely process. Try again or choose another model."* Both suggestions are wrong: retrying hits the same wall deterministically, and another model has the same 1 MiB ceiling. Rivet's own limit is presented as the provider's fault, with no way forward.
- **Fix shape:** raise or stream-to-disk the cap for agent turns, and name Rivet as the limiter with a real recovery ("the reply was too large to hold; Rivet can write it in parts — continue?").

### F04 — The same cap and message break the model list, inside the screen that asks you to choose a model
- **Severity:** wrong-result
- **Status:** CONFIRMED
- **Evidence:** `Http.kt:49` (`MAX_PROVIDER_JSON_BODY_BYTES = 1024 * 1024`), `Http.kt:52-55` (`readBoundedBody` throws `ResponseTooLarge` from `contentLength()` too). Used by every client's `listModels`: `OpenAiCompatibleClient.kt:31`, `AnthropicClient.kt:42`, `GeminiClient.kt:38`, `ChatGptPlanClient.kt:45`.
- **Trigger:** a provider whose `/models` response exceeds 1 MiB — realistic for OpenRouter (hundreds of models with full metadata) and for self-hosted gateways that return everything.
- **What the user sees:** the model picker shows "The provider sent more data than Rivet can safely process. Try again or choose another model." — a message telling the user to choose a model, in the screen whose only job is to list models. Setup is a dead end.
- **Fix shape:** stream the model list and keep only `id`/limits as it parses, or drop the cap for this endpoint and cap the retained model count instead.

### F05 — A mid-stream error deletes the half-written answer the user just watched arrive
- **Severity:** data-loss
- **Status:** CONFIRMED
- **Evidence:** `AgentLoop.kt:124-150` — the partial text is persisted **only** in the `catch (e: CancellationException)` branch (`:144-148`). A `ProviderError` thrown from `requestOnce()` bypasses that and propagates. `ChatViewModel.kt:721-726` catches it and calls `stableFailure`, which at `ChatViewModel.kt:916-931` sets `streamingText = ""` and rebuilds `messages` from `durable` — a list that never contained the partial because `append(assistant)` was never reached.
- **Trigger:** any provider or network error after the first delta: connection reset, 5xx mid-stream, a malformed chunk (`Http.kt:269-272` turns any `onEvent` exception into `InvalidResponse`), or a context-overflow retry (`AgentLoop.kt:126-127` deliberately rethrows once `streamed.isNotEmpty()`).
- **What the user sees:** a long answer writes itself out word by word, then the whole thing disappears and is replaced by "The network request failed." Pressing Stop preserves the partial text; the network failing does not. That asymmetry is the bug.
- **Fix shape:** persist non-blank `streamed` text before rethrowing any error from the request path, the way the cancellation branch already does.

### F06 — A tool call cut off by the output-token limit discards the entire turn, on every provider
- **Severity:** data-loss
- **Status:** CONFIRMED
- **Evidence:** `OpenAiCompatibleClient.kt:169-173` (`expectedReason = if (tools.isEmpty()) "stop" else "tool_calls"`, then `throw IncompleteGeneration` on any mismatch — including `"length"`); `AnthropicClient.kt:271-274` (any `stop_reason` outside `end_turn`/`stop_sequence`/`refusal` throws, so `max_tokens` throws); `GeminiClient.kt:205-207` (`finishReason != "STOP"` throws, so `MAX_TOKENS` throws). `AgentLoop.kt:124-142` only recovers from `ContextOverflow`, never from `IncompleteGeneration`.
- **Trigger:** a large `write_file`/`apply_patch` whose arguments exceed the model's output ceiling. The provider truncates mid-JSON, the arguments string is invalid or the finish reason is a length cut, and the client rejects the whole response.
- **What the user sees:** "The model stopped before finishing its response. Try again or choose another model." Retrying sends the same request to the same ceiling, so it fails identically forever. Any valid text the model emitted before the tool call in that same turn is lost too.
- **Fix shape:** on a length cut, keep the turn and hand the model an error result telling it to write the change in smaller pieces, instead of discarding the response.

### F07 — Responses-API stream errors are silently dropped and surface as a parse failure
- **Severity:** wrong-result
- **Status:** POTENTIAL — confirm by capturing a `/responses` stream that emits a top-level `{"type":"error", ...}` event (overload, mid-stream rate limit)
- **Evidence:** `ChatGptPlanClient.kt:166-208` — `accept()` switches on exactly five event types (`response.output_text.delta`, `response.completed`, `response.failed`, `response.incomplete`, `response.output_item.added`, plus argument deltas). A top-level `error` event matches no branch and is discarded. `ChatGptPlanClient.kt:213` then reports `InvalidResponse("incomplete stream")`. (`response.refusal.delta` and `response.output_item.done` are likewise unhandled.)
- **Trigger:** a stream-level error event, which the Responses API uses for exactly the conditions users hit most (capacity, moderation, internal failure).
- **What the user sees:** "The provider returned a response Rivet could not parse." The provider's actual, actionable reason is discarded and never shown.
- **Fix shape:** handle the `error` event type and map it through `providerMessage`, as the other three event types already are.

### F08 — Editing failure codes reach the model with no recovery instruction
- **Severity:** dead-end
- **Status:** CONFIRMED
- **Evidence:** `SafAgentWorkspace.kt:125` (`throw AgentWorkspaceFailure(e.reason.name.lowercase())`) flattens every `WorkspaceFailure` reason to a bare code. `AgentToolError.kt:10-34` (`actions`) has entries for `unsafe_entry`, `stale_target`, `destination_exists`, etc., but **none** for `conflict`, `patch`, `missing`, `too_large`, `binary`, `limit`, `duplicate`, `not_file`, `not_directory`, `root`, `permission`. `AgentToolError.kt:47-54` then emits only `{"error":"<code>"}` — no `required_action`, no `retryable`.
- **Trigger:** the single most common agent failure: `apply_patch` whose `old_text` does not match exactly once (`WorkspaceText.kt:81-89` → `Reason.PATCH`), or a write against a file changed elsewhere (`Reason.CONFLICT`).
- **What the user sees:** "Failed  apply_patch" in the activity row with nothing else. The model received `{"error":"patch"}` and has to guess. Note the irony: every one of these reasons already carries a complete, well-written explanation in `WorkspaceFailure.kt:4-19` ("Each patch must match exactly once. No changes were written.") — the message is written, then thrown away one function before it reaches the model.
- **Fix shape:** add the missing codes to the `actions` map, or carry `Reason.message` through instead of the lowercased name.

### F09 — The same missing codes also defeat the no-progress guard, so one uneditable file burns up to 200 model turns
- **Severity:** hang
- **Status:** CONFIRMED
- **Evidence:** `AgentToolError.kt:35-41` (`deterministic`) lists the codes that register as repeatable failures. `too_large`, `binary`, `conflict`, `patch`, `missing`, `limit`, `not_file`, `duplicate`, `root`, `permission` are all absent. `AgentLoop.kt:223-235` can only stop the run when a code is in that set. `AgentLoop.kt:91` and `AgentLoop.kt:437` cap the loop at `RUNAWAY_MODEL_ITERATIONS = 200`.
- **Trigger:** a model that retries a failing edit (the normal model behaviour when the error carries no instruction — see F08). Because the identical call never registers as a deterministic failure, nothing stops it.
- **What the user sees:** a long, expensive, visibly looping turn — each retry is a full provider request. It ends with "Rivet stopped after reaching its safety limit. Try a smaller request." (`ChatViewModel.kt:815`), which blames the size of the request for a loop caused by a missing error message. Tokens are spent and the user learns nothing.
- **Fix shape:** treat any error carrying no `required_action` as non-retryable for the purposes of the progress guard, or add these codes to `deterministic`.

### F10 — No file over 1 MiB can be edited, ever
- **Severity:** dead-end
- **Status:** CONFIRMED
- **Evidence:** `WorkspaceText.kt:14` (`const val MAX_BYTES = 1024 * 1024`), enforced at `WorkspaceText.kt:48` (read), `:61` (write) and `:89` (patch); also `SafWorkspace.kt:412` for the SAF path. Surfaces as `{"error":"too_large"}` via F08.
- **Trigger:** `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, generated `.d.ts` files, data fixtures, minified sources — the exact files an agent gets asked to update in real projects.
- **What the user sees:** the agent cannot touch the file, gets no explanation, and (per F09) may loop on it. The user is likely to conclude the model is stupid rather than that Rivet refused.
- **Fix shape:** allow streaming line-range edits above the in-memory limit, and at minimum return an explanatory result naming the limit and offering `apply_patch` on a smaller region.

## 2. The agent loop

`AgentLoop` is well-built: runaway ceilings, correlated tool results, checkpoint reservations, deterministic-failure tracking, and a clear stop-reason enum. The defects below are gaps in the vocabulary it hands the model, not flaws in the structure.

### F11 — One symlink makes a project permanently unsyncable
- **Severity:** hang
- **Status:** CONFIRMED (this verifies known bug #6)
- **Evidence:** `WorkspaceMirror.kt:374` (`Files.isSymbolicLink(child) -> throw MirrorFailure("unsafe_entry", name)`), `WorkspaceMirror.kt:394` (any entry that is neither a directory nor a regular file → `unsafe_entry`), `WorkspaceMirror.kt:201-202` (rethrown, not converted). Consequence chain: `RuntimeController.kt:45-48` (`prepare()` → `dirty` → `sync_required`), `RuntimeController.kt:184` (`commandBlocker` → `sync_required`), `AgentLoop.kt:368-374` (`runtimeStopCode` → `RuntimeBlocked` → the run stops).
- **Trigger:** anything that leaves a symlink or special file in the tree. `npm install` creates them in `node_modules/.bin`; `python -m venv` creates `bin/python`; `pnpm`, cargo and many build tools do the same. `localSnapshot()` walks the whole tree and throws on the first one it meets, before it can snapshot anything.
- **What the user sees:** every subsequent `run_command` returns `sync_required`, every run stops with "Rivet could not safely reconcile project changes. Stop and review the project before retrying." The only escape is Discard pending changes, which throws away **all** the command output that has not been synced yet. The project is stuck in pending-changes limbo with a real recovery path that costs the user their work. This is bug #6 confirmed, and the symlink case is the one that fires in ordinary projects.
- **Fix shape:** skip and report unsafe entries per-path (as `SafWorkspace` already does for the SAF side) instead of aborting the whole snapshot, and let the sync proceed for the rest of the tree.

### F12 — One file changed by another app blocks the entire sync
- **Severity:** hang
- **Status:** CONFIRMED
- **Evidence:** `WorkspaceMirror.kt:129-133` — the sync scans the union of baseline, SAF and local keys and returns `MirrorSyncResult(MirrorSync.Conflict, difference)` on the *first* entry that differs on both sides. Nothing else in the tree is written.
- **Trigger:** the user edits any one file in another editor while unsynced command output is waiting. Also, an interrupted write that left a partially written SAF file (which then differs from both baseline and mirror).
- **What the user sees:** "pending project changes" that will not clear, no indication of which file is the problem (the path is carried in `MirrorSyncResult.path` but the run-command path drops it into a bare `"conflict"` sync state), and no per-file resolution. Same discard-or-nothing choice as F11.
- **Fix shape:** report the blocking path in the tool result and sync everything that is unconflicted.

### F13 — Every read tool re-hashes the whole project, and every command after an edit re-copies it
- **Severity:** annoyance (the one that makes the app feel broken on a cheap phone)
- **Status:** CONFIRMED
- **Evidence:** `AgentToolExecutor.kt:375-378` — `readOnly` wraps *every* read tool (`read_file`, `list_directory`, `search_files`, `git_status`, `git_diff`) in `requireSafCurrent()`. `RuntimeController.kt:87-90` → `WorkspaceMirror.hasLocalChanges()` → `WorkspaceMirror.kt:88-92` → `localSnapshot()` at `:363-401`, which SHA-256s **the content of every file in the worktree**. Separately, `RuntimeController.kt:45` → `prepare()` → `WorkspaceMirror.kt:79-83`: after any SAF-side change (i.e. after any agent edit) the baseline no longer matches, so `materialize()` runs a **full re-copy of the entire project** from SAF into app storage (`:296-332`, `:350-353`), with a per-file space check at `:350`.
- **Trigger:** normal use. The agent alternates read → edit → command dozens of times per task.
- **What the user sees:** a project with a few thousand files makes every tool call take seconds, and every `run_command` after an edit pauses while the whole tree is copied again. No spinner (see F26), so it reads as a frozen app. This is the "slow on real phones" complaint, mechanically explained.
- **Fix shape:** make `localSnapshot` incremental (mtime+size short-circuit before hashing) and make `materialize` copy only paths whose fingerprints differ.

### F14 — While a command runs, Undo and Retry are silently dead
- **Severity:** hang
- **Status:** CONFIRMED
- **Evidence:** `RuntimeController.kt:39` declares one `Mutex` and `:43` takes it around the *entire* `runCommand`, including the whole `active.sync()` at `:74`. Every other entry point takes the same mutex: `requireSafCurrent` `:87`, `gitStatus` `:92`, `beginCheckpoint` `:100`, `finishCheckpoint` `:108`, `recordCheckpointPost` `:116`, `checkpointMatchesPost` `:124`, `checkpointTurnChanges` `:137`, `undoLastCheckpoint` `:142`, `agentFailureState` `:173`, `commandBlocker` `:181`, `retryPendingChanges` `:239`, `discardPendingChanges` `:244`.
- **Trigger:** a long command (`MAX_COMMAND_TIMEOUT_MS` is 30 minutes, `AgentToolExecutor.kt:654`) while the user taps Undo, "Try again", or Discard.
- **What the user sees:** the button does nothing. No spinner, no disabled state, no explanation — the tap is simply swallowed until the command finishes, possibly half an hour later, at which point the action fires unexpectedly (or the composable has already been disposed). This is the worst kind of UI dishonesty: the app accepted the gesture and hid the fact that it queued it.
- **Fix shape:** take the mutex for the mirror-touching phases only, not across process execution, and disable the buttons while it is held.

### F15 — A failed Undo leaves the project holding the new content and the mirror holding the old
- **Severity:** data-loss
- **Status:** CONFIRMED
- **Evidence:** `RuntimeController.kt:142-160`. Order is: `stageUndo` → `active.installCheckpoint(staged)` (mirror now replaced with pre-turn content) → `active.sync()` `:157` → `if (sync.state == Ok || NoChanges) store.markUndone(record.id)` `:158`. If `sync()` throws, there is no `catch`: `markUndone` is skipped, no rollback happens, and the exception propagates.
- **Trigger:** storage full, a path in the restored tree that cannot be written to SAF, or an `unsafe_entry` during the sync's own snapshot (the checkpoint may have restored a tree the mirror snapshot rejects).
- **What the user sees:** "Undo failed" (or a sync failure banner), while the project still contains the *new* content and the internal mirror now contains the *old* content. The next command reports `sync_required`. The checkpoint is still marked live, so tapping Undo again repeats the same half-applied operation. The user cannot tell which version of their files is real.
- **Fix shape:** treat a failed post-restore sync like the existing `installCheckpoint` failure path — mark the checkpoint unusable and surface a single, explicit "your project may be in either state" recovery.

### F16 — Command output is capped at 8 KB, and the middle is dropped
- **Severity:** wrong-result
- **Status:** CONFIRMED
- **Evidence:** `CommandProcess.kt:138` (`BoundedCapture(private val half: Int = 4096)`), `:147-158` (head fills 4 KB, then a 4 KB ring buffer for the tail), `:160-166` (`"$first\n… [output truncated] …\n$last"`). The 24 KB limit the executor believes it enforces (`AgentLoop.kt:440`) is never reached because the capture is already 8 KB.
- **Trigger:** any real build or test run. A Gradle/Maven/npm failure prints setup noise first and the actual compiler error somewhere in the middle.
- **What the user sees:** the agent reports the build failed, then guesses at the cause, because all it received was the first 4 KB (usually "Starting a Gradle Daemon…") and the last 4 KB. `stdout_truncated: true` tells it something was lost but not how to get it, and there is no re-run-with-filter affordance.
- **Fix shape:** keep a larger window, or grep-prioritise retained lines (error/fail/exception) before truncating.

### F17 — Exit 126 means two different things, one of them silent
- **Severity:** wrong-result
- **Status:** CONFIRMED
- **Evidence:** `terminal-emulator/src/main/jni/command.c:64-71` — the child `_exit(126)` for `setsid`, `dup2` or **`chdir`** failure, and `_exit(127)` if `/system/bin/sh` itself cannot be spawned. Neither writes to stderr. Genuine "found but not executable" (`./node: Permission denied`) is produced by the shell itself, which *does* write to stderr.
- **Trigger:** a `cwd` that exists in the mirror but vanished, or any child setup failure; and, separately, the downloaded-binary case from F21.
- **What the user sees:** `exit_code: 126` with completely empty `stdout` and `stderr`. The model has no way to distinguish "your file is not executable" from "Rivet's process setup failed", so it tries chmod, then redownloads, then tries a different path.
- **Fix shape:** write a diagnostic to stderr before `_exit(126)` in the child, and use a distinct code for Rivet-internal setup failures.

### F18 — A project over 50,000 files cannot be edited at all, and the message blames storage
- **Severity:** dead-end
- **Status:** CONFIRMED (a sibling of bug #6, but in the checkpoint path rather than the sync path)
- **Evidence:** `TurnCheckpoint.kt:176` and `:186` (`throw CheckpointFailure("checkpoint_limit")` when `entries.size > MAX_ENTRIES` or `bytes > MAX_CONTENT_BYTES`), constants at `:305-306` (`MAX_ENTRIES = 50_000`, `MAX_CONTENT_BYTES = 1 GiB`). `AgentLoop.kt:328-337` converts any `beforeMutation` exception into `checkpoint_unavailable` and stops the run. Messages: `AgentToolError.kt:16` ("Resolve workspace or storage changes before retrying the mutation.") and `ChatViewModel.kt:818-824` ("Rivet couldn't prepare a safe Undo, so it stopped before changing files. Try again.").
- **Trigger:** any repository with `node_modules` installed, a large `build/` tree, or a media asset folder. `scan()` walks everything and only skips `.git` (`TurnCheckpoint.kt:169`).
- **What the user sees:** every edit refuses with a message about *storage*, and "try again" never works because the project size has not changed. There is no indication that 50,000 files is the ceiling, and no way to exclude a directory — the user's only path is to delete `node_modules` and hope.
- **Fix shape:** honour a per-project ignore list (`.gitignore` or a Rivet list) in `scan()`, and name the actual limit and the offending size in the error.

### F19 — Checkpointing copies the whole project on every mutating turn, on top of the mirror
- **Severity:** annoyance
- **Status:** CONFIRMED
- **Evidence:** `TurnCheckpoint.kt:47-70` — `begin()` zips the entire worktree (`zip.setLevel(1)`) before the first mutation of a turn, writing a second full copy of the project into app storage. `TurnCheckpoint.kt:305-309` (`MAX_HISTORY_BYTES = 2 GiB`, `MAX_RETAINED = 3`). `prune()` `:270-287` runs only from `finish()`.
- **Trigger:** ordinary use on a project of any size. The mirror (`WorkspaceMirror`) is already a full copy of the project (F13); checkpoints add up to three more.
- **What the user sees:** a 300 MB project can occupy well over 1 GB of app storage, and the first edit of each turn pauses while the zip is written. When storage runs out the failure surfaces as `checkpoint_unavailable` (per F18), i.e. "resolve storage changes" — occasionally true, but with no guidance about what is eating the space.
- **Fix shape:** store a content-addressed delta per turn rather than a full archive, or use hard links for unchanged files.

### F20 — A crash during mirror refresh can leave a project permanently unusable, with no in-app recovery
- **Severity:** data-loss
- **Status:** POTENTIAL — confirm by killing the process (`am force-stop`) during `materialize()`'s final `removeTree(previous)`
- **Evidence:** `WorkspaceMirror.kt:427-429` — on recovery, if `previous` exists and does not match its own baseline, `recover()` throws `MirrorFailure("previous_dirty")`. `removeTree` (`:441-453`) deletes file by file, so a process death mid-delete leaves `previous` with fewer entries than its baseline, which fails that comparison. `recover()` is called first in `prepare()`, `sync()`, `discardPendingChanges()` (`:207-215`) and `installCheckpoint()`, so every operation — including the discard that is supposed to be the escape hatch — throws before it can do anything.
- **Trigger:** process death or Android kill during mirror materialisation or checkpoint install, in a window that is small but entirely reachable on a memory-constrained phone (which is the target device class).
- **What the user sees:** every command and every edit fails with an opaque `previous_dirty`, restarting the app does not help, and the only documented recovery (Discard pending changes) is itself blocked. The realistic user fix is clearing app data, which also destroys every conversation.
- **Fix shape:** treat a partially deleted `previous` as reconcilable — delete the remainder instead of blocking — and surface a visible "Rivet could not recover this project's runtime copy; reset it?" action.

## 3. Commands, mirror workspace, checkpoints

### F21 — The model is never told what the sandbox cannot do
- **Severity:** dead-end
- **Status:** CONFIRMED (this verifies known bug #5)
- **Evidence:** the system prompt is `ChatViewModel.kt:1104-1105` and contains no statement of runtime capability — no mention of PATH, no toolchain inventory, no statement that downloads lose their executable bit, no output or size ceilings. The `run_command` tool description (`AgentToolExecutor.kt:703`) says only that "Rivet's capability and workspace checks always apply". The facts the model is missing are in the code: `RuntimeController.kt:270-277` sets `PATH=/system/bin:/system/xbin:/vendor/bin` (no node, python, git, npm, gradle, or Termux binaries), `HOME` and `TMPDIR` point at app-private directories rather than the project (`:271-273`), `command.c:69` runs everything through `/system/bin/sh -lc`, and `WorkspaceMirror.kt:353` materialises files with `FileOutputStream` so no executable bit survives the copy from the project.
- **Trigger:** any task that assumes a normal developer toolchain — "run the tests", "install dependencies", "build it".
- **What the user sees:** the agent spends turns discovering the environment by failure: `node -v` fails, so it downloads a Node binary with `download_file`, the binary does not run, so it retries a different download, and the project accumulates unused runtime directories (which then trip F18/F19 on size). The user watches a confident agent flail against a constraint nobody mentioned. The prompt does say downloads are "never installed or run", but it never says *why*, or what to do instead.
- **Fix shape:** add one paragraph to the system prompt listing the actual shell environment, the absence of a package manager, and that downloaded binaries cannot be executed.

## 4. Android lifecycle

### F22 — Switching apps mid-run kills the turn with a network error
- **Severity:** hang
- **Status:** CONFIRMED (this verifies known bug #2)
- **Evidence:** the run is launched in `viewModelScope` (`ChatViewModel.kt:327` onwards) and nothing in the chat path acquires a foreground service or wake lock. The only `startForeground` call in the codebase is for previews: `RuntimeController.kt:224` → `ManagedProcesses.ensureForegroundService` (`ManagedProcesses.kt:232-239`) → `PersistentProcessService.kt:105`. A repository-wide grep for `WakeLock`/`PARTIAL_WAKE_LOCK` returns nothing.
- **Trigger:** backgrounding Rivet during a turn — which on Android 12+ can mean the process is frozen and the socket is torn down or left half-open.
- **What the user sees:** the answer stops, and on return the chat shows a network error. A long write that was 90% done is gone (per F05). Nothing warns the user that leaving the app aborts the work, and there is no notification or ongoing-run affordance to come back to.
- **Fix shape:** run the agent turn in a foreground service (the preview service already exists as a model), or at minimum warn before the first backgrounding and persist the partial.

### F23 — After a process death, a dead turn looks like a normal empty turn
- **Severity:** annoyance
- **Status:** CONFIRMED
- **Evidence:** `CodingSessions.kt:96-97` and `:537-543` — `recoverInterrupted` synthesises "Interrupted  <tool>" results, but **only** when the last stored message has a pending tool call (`:539`). If the process died after the user message was persisted (`ChatViewModel.kt:461`) and before any assistant message, the last message is a user message, `hasPendingToolCall` is false, and the function returns unchanged. A repository-wide grep for `interrupted` under `ui/` returns nothing, so no surface tells the user anything either way.
- **Trigger:** process death or a kill during the first seconds of a turn, before the first streamed token — common on a memory-constrained phone.
- **What the user sees:** the prompt they sent is in the conversation with no reply, no error, and no indication that the turn ever ran or failed. They cannot tell whether to wait, retry, or that their request was silently dropped.
- **Fix shape:** persist a turn-in-progress marker and render a "this turn was interrupted — retry?" row on restore.

### F24 — Backgrounding during a command can report a timeout for work that succeeded
- **Severity:** wrong-result
- **Status:** POTENTIAL — confirm by starting a long command, backgrounding, and returning after the timeout
- **Evidence:** `CommandProcess.kt:80` (`withTimeoutOrNull(timeoutMs) { exited.await() }`) measures wall-clock time across the coroutine, while `waitFor` runs on its own thread (`:66-69`). A frozen process accumulates elapsed time without the coroutine running, so on unfreeze the timeout branch (`:81-84`) can win even though `exited` is already completed.
- **Trigger:** any command longer than its remaining budget while the app is backgrounded.
- **What the user sees:** a tool result carrying a real `exit_code: 0` **and** `timed_out: true`, which is contradictory; the activity row may show Exit 0 while the command was force-killed for a timeout it did not hit.
- **Fix shape:** check `exited.isCompleted` before treating the timeout branch as a real timeout.

### F25 — Rotating the phone silently kills a ChatGPT sign-in
- **Severity:** wrong-result
- **Status:** CONFIRMED
- **Evidence:** `ProviderEditor.kt:83` (`rememberCoroutineScope()`), the sign-in launched in it at `:166`, and `ProviderEditor.kt:93-96` (`DisposableEffect(chatGptSession) { ... onDispose { session?.cancel() } }`). `signingIn`/`signInError` are `remember`, not `rememberSaveable` (`:84-85`).
- **Trigger:** any configuration change — rotation, dark-mode toggle, split-screen resize — between tapping "Continue with ChatGPT" and the browser redirect returning.
- **What the user sees:** the browser redirect fails to load; returning to Rivet shows an idle "Continue with ChatGPT" button and no error text at all. Nothing explains that the attempt died.
- **Fix shape:** run the sign-in in the ViewModel scope and keep its error in the editor state.

## 5. UI honesty

### F26 — There is no progress indicator anywhere in the conversation, and the status line hides during the longest work
- **Severity:** annoyance
- **Status:** CONFIRMED (this verifies known bug #3)
- **Evidence:** `ChatScreen.kt:636` — `val showActivity = state.activity != null && streamingText.isBlank() && liveOperation == null`. `ChatScreen.kt:631-634` computes `liveOperation` and uses it *only* to suppress that row; it renders nothing itself. A repository-wide grep for `CircularProgressIndicator`/`LinearProgressIndicator` finds them only in `ui/chat/ModelSheet.kt:178`, `ui/provider/ProviderEditor.kt:234,295` and `ui/provider/UpdatesSection.kt:36,52,55` — **none in the chat surface**. The streaming preview itself does work, throttled at 80 ms (`ChatViewModel.kt:608-613`), so the word-by-word feel exists; what is missing is any signal that the app is alive when text is *not* arriving.
- **Trigger:** every turn. Specifically: while a tool runs (the activity text is suppressed by `liveOperation != null`), and during the dead air between a tool result and the next delta.
- **What the user sees:** during a 10-minute command the only signal is a static "Running" text row (`AgentActivityProjection.kt:91`), identical whether the command is 2 seconds or 10 minutes old, with no elapsed time and nothing moving. A stalled stream (F01) and a slow one look exactly the same. The user cannot distinguish working from stuck, which is the exact complaint that opened this audit.
- **Fix shape:** render a spinner (or an elapsed-time tick) whenever `state.streaming`, unconditionally, independent of `streamingText` and `liveOperation`.

### F27 — The provider's own error text is deliberately discarded, and a failed turn has no retry
- **Severity:** annoyance
- **Status:** CONFIRMED
- **Evidence:** `ProviderError.kt:23-24` ("Keep provider wire messages out of normal Chat; they may contain implementation details or request fragments") — `ProviderMessage.text()` at `:49` returns the fixed string "The model provider couldn't complete this request. Try again or check its settings." regardless of what the provider said. `ChatViewModel.kt:840-841` sets `errorAction` only for `SYNC_RECOVERY_CODES`, otherwise `null`; `ChatScreen.kt:695` renders no button for a null action.
- **Trigger:** the most common failures — a 400 with a specific complaint, a moderation refusal, "insufficient balance", a proxy's "model overloaded".
- **What the user sees:** "The model provider couldn't complete this request. Try again or check its settings." with no detail and no button. The user's prompt has been consumed, so recovering means retyping it from memory. The specific sentence that would have solved the problem in one read is available and thrown away.
- **Fix shape:** show a sanitised, length-capped provider message (the code already bounds and truncates it in `Http.kt:67-78`), and give every failed turn a Retry action.

## 6. Provider settings and storage

### F28 — Losing the Android keystore turns Settings into a permanent dead end
- **Severity:** hang
- **Status:** CONFIRMED path; POTENTIAL trigger (keystore entry lost or invalidated)
- **Evidence:** `ProviderStore.kt:116-121` — `decodeForUse` throws `IllegalStateException("provider header decryption failed")` (the `?:` at `:120`) when a header cannot be decrypted. That flow backs the provider list, so `ProvidersViewModel.kt:56-58` catches it into "Rivet couldn't securely read provider settings. Re-enter any custom headers in Settings." — advice that cannot be followed, because `save()` calls `migrateLegacyHeaderValues()` (`ProviderStore.kt:53-54`, `:93-94`) which runs `check(secrets.decryptProviderHeader(...) != null)` and throws the same error before any write. The message is rendered with no action (`SettingsScreen.kt:162-166`) and no reset API exists anywhere in the codebase.
- **Trigger:** the keystore entry for `rivet_api_key_aes_v1` disappears or is invalidated — device restore, "clear credentials", or an OEM keystore wipe — while at least one provider has custom headers.
- **What the user sees:** the provider list is empty ("Choose a provider below…"), a red error line explains nothing actionable, and every Save answers "Rivet couldn't save these provider settings securely. Try again." Forever. Sending fails too. The only escape is clearing app data, which destroys all conversations.
- **Fix shape:** on decrypt failure, drop the unreadable header (or config) and rewrite the store so the list renders and can be edited.

### F29 — One unreadable stored config silently wipes every other provider on the next save
- **Severity:** data-loss
- **Status:** POTENTIAL — confirm with a stored `configs` value this build cannot deserialise (enum/`@SerialName` drift, or a downgrade after an upgrade), then any save
- **Evidence:** `ProviderStore.kt:49-51` — `decode()` catches everything and returns `emptyList()` ("unreadable store degrades to empty"). `ProviderStore.kt:57` then does `val current = decode(prefs[configsKey]).toMutableList()` and `:60` writes that list back.
- **Trigger:** version drift in `ProviderConfig`/`ProviderType`, which the project's own schema history makes plausible.
- **What the user sees:** after tapping Save on one provider, every other provider is gone from the list. Their keys and headers are still on disk, orphaned and unreachable.
- **Fix shape:** when `decode` fails, throw instead of writing back an empty list.

### F30 — A keystore RuntimeException crashes the app while saving an API key
- **Severity:** crash
- **Status:** POTENTIAL — confirm on a device whose keystore throws `ProviderException`/`IllegalStateException`
- **Evidence:** `SecretStore.kt:25-37` catches only `GeneralSecurityException` and `IOException`; the same narrow catch appears at `:53-57` and `:67-71`; key creation (`:147-167`) is unguarded. The caller at `ProvidersViewModel.kt:386-387` does not catch either.
- **Trigger:** a vendor-forked or degraded keystore, most likely on the cheap devices this app targets.
- **What the user sees:** Rivet closes with no message and the key is not saved.
- **Fix shape:** catch `RuntimeException` at the encrypt/decrypt entry points and return failure.

### F31 — Deleting or selecting a provider has no error handling
- **Severity:** crash
- **Status:** POTENTIAL — confirm with a DataStore write failure (full disk) or the F30 throw
- **Evidence:** `ProvidersViewModel.kt:415-421` and `:424-425` — bare `viewModelScope.launch { store.delete(id) }` / `{ store.setActive(...) }`, while every sibling write is guarded (`:394-403`, `:140-147`). The store operation itself is a non-atomic three-step sequence: `ProviderStore.kt:66-72` (edit → `setActive` → `clearApiKey` → `clearOAuthBundle`).
- **Trigger:** a write failure at the moment the user taps the trash icon or a radio button.
- **What the user sees:** a crash; after restart the provider may be gone from the list while `active_id` still names it, so sending reports "The selected provider no longer exists."
- **Fix shape:** wrap both launches and surface the failure through `loadError`.

### F32 — Every file operation re-walks the whole path from the root
- **Severity:** hang
- **Status:** CONFIRMED
- **Evidence:** `SafWorkspace.kt:342-355` — `resolve()` loops over `path.segments`, and each segment runs `children(entry, 5000)`, a full `resolver.query` of that directory (`:356-358`) with `requireGrant()` re-reading `resolver.persistedUriPermissions` on every query (`:363`) and every `io()` (`:468`). A write resolves twice (`:196`, `:206`); `applyTextPatch` resolves three times.
- **Trigger:** any edit of a file roughly 9 levels deep, in a project whose directories contain thousands of entries (`node_modules`, `build/`, `.git` are all in the same tree).
- **What the user sees:** multi-second freezes per file write, which compound with F13 into an app that feels hung while it is actually working.
- **Fix shape:** memoise `children()`/`documentId` per parent for the duration of one operation.

## Top 10 by user pain

Ranked by how much damage a real user experiences on a real phone, not by severity label.

1. **F01 — a heartbeat-only stream hangs the reply forever.** The flagship complaint. No error, no timeout, no escape except Stop, and a dead stream is indistinguishable from a slow one.
2. **F02 — a provider without `[DONE]` throws away a complete answer** and calls it a parse failure. Silent incompatibility with whole classes of providers, and the total loss of an answer the user already read.
3. **F22 — backgrounding the app kills the turn.** On a phone, switching apps is constant. Every interruption costs the user's work and returns a misleading network error.
4. **F05 — a mid-stream error deletes the half-written answer.** The user watches 2,000 words appear and then evaporate; Stop would have kept them. Pure trust damage.
5. **F11 — one symlink makes the project permanently unsyncable.** `npm install` — the most ordinary action in the product's target use case — strands the project behind a banner whose only escape deletes unsynced work.
6. **F13 — every read re-hashes the project and every command after an edit re-copies it.** Not dramatic, just relentless: it makes the app feel broken on exactly the cheap devices it targets, and it quietly explains a dozen "Rivet is slow" reports.
7. **F18 — a project over 50,000 files cannot be edited, and Rivet blames storage.** Any repo with `node_modules` installed becomes read-only, with a message that points the user at the wrong problem and a "try again" that can never work.
8. **F03 — the 1 MiB cap kills big-file work and blames the provider.** Rivet's own ceiling, presented as the provider's fault, with two suggestions that both fail deterministically.
9. **F28 / F29 — provider settings can dead-end or wipe the provider list.** Keystore loss makes Settings permanently unsavable (only app-data reset fixes it); a decode failure silently deletes every other provider.
10. **F14 — Undo and Retry are silently dead while a command runs.** A swallowed tap during the 30-minute window, with no spinner and no disabled state, then the action fires much later out of context.

Close runners-up: F09 (a missing error message turns one uneditable file into 200 model turns) and F10 (any file over 1 MiB is untouchable — lockfiles included).

## Clean / negative results

Recorded so you know these were opened, not skipped.

- **Updater (`GitHubUpdates.kt`, `UpdateApks.kt`, `UpdatesViewModel.kt`).** The hypotheses did not reproduce. Redirects are pinned to https/443 with a host allowlist, metadata and APK sizes are capped, partial downloads are deleted, signer set + `versionCode` + `versionName` + package are verified with `ApkVerifier` before use, output goes to MediaStore Downloads (discoverable) or the user's SAF pick, and "Check for updates" is never a silent no-op. Remaining problems are annoyances only.
- **Conversation persistence (`CodingSessions.kt`).** Real SQLite with `beginTransaction`/`setTransactionSuccessful` around every mutation, prefix-consistency checks (`CodingSessions.kt:114-116`), a correlated-tool-result invariant (`:118-123`), and no swallowed durable-write exception. The "write straight to the real file" failure class does not apply here. Its one soft spot is the silent projection truncation under corruption (`:679-690`, `:721`).
- **`ApprovalPolicy.kt`.** No bypass found. `decide()` returns `Blocked("approval_unavailable")` rather than `AskUser` when a tool has no approval object (`:21`), so the `requireNotNull` at `AgentLoop.kt:312` cannot fire.
- **`AgentLoop` structure.** Runaway ceilings, `NonCancellable` persistence for completed protocol events, correlated results for every un-executed call in a batch, checkpoint reservation before side effects, and a stop-reason enum whose user-facing text is distinct and honest (`ChatViewModel.kt:808-833`). The empty-response case is handled (`:811-813`).
- **`MainActivity.kt` / `RivetApplication.kt`.** No rotation or process-death data loss; ViewModels are Activity-scoped and survive rotation, managed processes are Application-scoped, and the `OPEN_PROCESSES` extra is cleared after consumption.
- **`WorkspacePath.kt`, `AgentToolExecutor.path()`.** Rejects empty, `.`, `..`, blank segments, trailing dots, control characters, backslashes, and bounds depth and length (`AgentToolExecutor.kt:537-547`). Duplicate document ids are caught (`SafWorkspace.kt:342-353`).
- **`AutonomyStore.kt`, `UsageDiagnostics.kt`, `ProviderEditorState.kt`, `SupportSection.kt`, `HistoryScreen.kt`, `ProcessesScreen.kt`** (beyond the annoyance listed): no defects found. Buttons are correctly disabled while streaming/undoing and empty states are truthful.

## Summary

The provider and persistence layers are more careful than the reported symptoms suggest — the SQLite store, the updater, the approval policy and the agent loop's ceilings are all genuinely hardened, and several obvious failure classes were checked and came back clean.

The defects cluster in three places:

1. **The stream reader only knows two states, and it guesses wrong about both.** A missing sentinel and a real truncation produce the same "could not parse" error, and a heartbeat looks identical to progress. That single design choice generates F01, F02, F07.
2. **The error vocabulary handed to the model is narrower than the error vocabulary the code produces.** `WorkspaceFailure` writes excellent explanations and `AgentToolError` drops most of them, so the model retries blindly — F08, F09, F10, and the flailing in F21 all follow from that gap.
3. **Every per-file and per-turn boundary is either whole-tree or nothing.** Sync, snapshot, checkpoint, and materialise all fail as a unit, and all four re-walk or re-copy the entire project. That gives F11, F12, F13, F18, F20 and the "slow phone" feel that no single bug explains.

Nothing here requires an architectural change. The highest-value fixes are small: a delta-timestamp deadline in the read loop (F01), accepting a finish signal instead of a sentinel (F02), persisting partial text on any error path (F05), adding the missing codes to one map (F08/F09), and a foreground service for the turn (F22). Those five remove most of the user pain in the Top 10.
