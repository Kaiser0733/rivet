Audited source at `batch/surface-fix` / `7d28b6c822666a304d5e1d4b9dffb41eef7db184`, on `soul-audit`. This is a source audit, not a visual or interaction test. ## Design direction, reviewed against the brief

**Recommend: Workbench companion.** A phone-sized creative workspace that acknowledges the user's action with a small, precise response. Spend the distinctive visual gesture on a single completion moment in the existing turn fold: a short, restrained reveal of the existing outcome, with no invented progress or success claim. Everything else is quiet: familiar chat controls, left-aligned text, clear hierarchy, no decorative card fleet. Candidate light tokens: paper `#FFFFFF`, ink `#17212B`, secondary `#536271`, divider `#DCE3E9`, signal blue `#3567A7`; dark: canvas `#15191F`, ink `#F3F6F9`, secondary `#B8C3CE`, divider `#39444F`, signal `#89B5F2`. Candidate type: Android system sans, medium weight for titles and regular for messages; platform monospace only for commands. Motion: action-led fold 180 ms / 150 ms, one completion reveal at most 180 ms, honor reduced motion. Copy: direct, calm, concrete: “Choose a folder”, “Couldn't open that folder”. This fits an AI agent making real things on a small screen without turning the conversation into a dashboard.

Two alternatives, both retaining chat placement and behavior:

- **Field notes:** light `#FAFCFE`, ink `#1B2835`, secondary `#526677`, rule `#D7E2EA`, blue `#426D94`; dark `#17212A`, text `#EDF4F7`, secondary `#B3C7D1`, rule `#3D515E`, blue `#96C4DA`. System sans for all prose, mono for real paths; motion is nearly still, short state transitions; copy is observational and specific. Fits inspection-heavy work, but risks making chat feel like a logbook.
- **Pocket studio:** light `#FFFFFF`, ink `#242437`, secondary `#625F72`, rule `#E2E0EA`, violet `#6755A3`; dark `#1A1922`, text `#F5F3FA`, secondary `#C5BDD4`, rule `#494357`, violet `#C4B0F3`. System sans with medium titles, mono for actual code; one soft completion response and otherwise instant controls; copy is encouraging without celebration. Fits creative starters, but a broad violet treatment could make operational screens feel playful at the wrong time.

Process review: the first sketch used a warm cream surface and display serif; that was generic and unrelated to Rivet's working context, so it was discarded. The recommendation uses the existing system type and familiar app skeleton; it introduces no decorative brand furniture, new navigation, backend work, or chat rearrangement. Compare colors in both modes for contrast before adopting them; these are proposals, not measured accessibility results.

## Already-noted items: verification and boundaries

- **Raw `error: code —` in chat:** `ErrorRow` displays `displaySafeText(error)` in `ChatScreen.kt`; sanitization is not a human translation. I found `error:` in provider sign-in copy and `ProviderError.Server`, but did not prove the exact claimed prefix reaches an ordinary chat error from every source. Reproduce and trace the specific input before designing a presentation-only mapping; preserve useful details and retry actions.
- **Reply language drift:** model text is rendered through the chat message/markdown path. Code inspection cannot establish drift or its cause. Enforcing a response language is model/prompt behavior and out of scope; never rewrite the user's or model's words in UI.
- **Terminal buried:** confirmed as a card inside Tools, opened via the Processes header button. A new direct top-bar destination would change the chat layout/navigation and is outside this audit's permitted proposals.
- **Stale “Terminal: busy”:** `runtime/TerminalGovernor.kt` builds the busy string from activeCount and slots; `RivetApp.kt` passes a state line to Tools. Existence is proven, staleness is not; verify on device and trace state lifecycle. Any actual lifecycle correction is behavior work, out of scope.
- **Worker sheet:** fixed-height sheet, metadata and chip duplication confirmed above; actual crowding requires phone screenshots.
- **Welcome, icon labels, banner:** no dedicated welcome screen found in the inspected shell; no-provider/no-project/ready states perform that job. Header icons have content descriptions but no visible labels. ChatGPT-plan banner has a usage link; evaluate wording and conditions on a device. Adding labels that rearrange header is prohibited here.
- **Shared-storage sandbox explanation:** no matching explanatory copy found in the inspected UI and strings. Termux's approval text describes full Termux-user powers outside Rivet's sandbox in `runtime/TermuxBridge.kt`, a different context. Do not claim an existing shared-storage banner or weaken that warning.
- **Checkpoint prompt/diff:** duplication and missing diff in the row are confirmed. Whether `summary` is a truncated prompt for a particular run depends on the data; no diff can be conjured from the displayed fields.
- **Tools close:** no explicit panel close control confirmed, but scrim and Back work.
- **Long Thinking:** `chat/LiveStatus.kt` has a “Thinking” fallback; `ChatProcessGroups.kt` extracts live reasoning detail when available, and `ChatScreen.kt` shows reasoning previews. No-detail is conditional, not universal. Duration and actual provider output need observation.
- **Fold chevrons:** several are 14 dp in `ChatScreen.kt`; the icon's size is not necessarily the clickable target's size. Verify touch target and accessibility on device before declaring a failure.
- **Swipe typing:** composer is an `OutlinedTextField`; no relevant custom drag handler was found in that field. A keyboard gesture conflict needs reproduction with the affected IME and device; fixing gesture arbitration could change interaction behavior and is out of scope until diagnosed.

## Ranked surface-only proposals

Each is independently implementable and changes existing surfaces, not backend, models, storage, tools, permissions, or chat layout.

1. **Plain, consistent visible names and error presentation.** `ui/chat/ChatScreen.kt`, `ui/processes/ProcessesScreen.kt`, and relevant `app/src/main/res/values/strings.xml`: align the existing Processes/Tools accessibility label with the panel title; present known existing error text as a concise reason and action, keeping raw technical details available where applicable. Must not alter error classification, hide unknown errors, change retry semantics, or touch agent/provider code. Fixes an ambiguous top-bar action and machine-like error moments.
2. **One completion signature.** `ui/chat/ChatScreen.kt`, `ui/FoldReveal.kt`: make the existing finished-turn fold acknowledge completion with a single brief reveal of existing text, respecting system reduced motion. Do not change fold grouping, response content, chat positions or claim success for failed/stopped work. Fixes the abrupt transition from activity to outcome; test visually before adoption.
3. **Close affordance for Tools.** `ui/processes/ProcessesScreen.kt`, `ui/RivetApp.kt`: supply an explicit, accessible close action inside the existing panel header, retaining scrim and Back. Do not add a top-bar destination or move chat. Fixes the panel with no visible exit; verify available header space on a phone.
4. **Checkpoint rows use what they already know.** `ui/processes/ProcessesScreen.kt`: show summary once, time once, and a plain label for existing checkpoint type only when needed; retain Restore and Undo copy and confirmations. Do not fabricate changed-file counts or diffs, change checkpoints, or conceal recovery limitations. Fixes duplicated summaries and internal storage terms.
5. **First-run voice.** `ui/chat/ChatScreen.kt`, `ui/RivetVisuals.kt`, relevant strings: shorten explanations around the existing doodles and actions; adjust the ready-state approval claim to reflect that approval depends on settings, without making any promise about the current mode. Preserve all actions, project and provider requirements, existing chat geometry and truthful scope. Fixes setup reading as configuration before a conversation.
6. **Worker status legibility.** `ui/chat/WorkerSheet.kt`, `ui/chat/SubagentChip.kt`: distinguish current job from its status using existing type roles, and give the current selection an accessible state; retain every job, transcript, Continue/Stop and read-only behavior. Fixes repeated job labels and status buried in metadata without changing worker execution.
7. **Use existing status, never invent it.** `ui/chat/ChatScreen.kt`, `ui/chat/ChatProcessGroups.kt`: when actual reasoning/activity detail exists, keep it legible in the existing folded row; when absent, use a neutral waiting label. Do not synthesize progress, add backend polling, expose hidden reasoning, or rewrite model output. Fixes the generic Thinking moment only where available data supports it.
8. **Setup and specialist copy pass.** `ui/provider/SettingsScreen.kt`, `ui/local/ModelsScreen.kt`, `ui/starter/StarterGallery.kt`, `ui/browser/BrowserScreen.kt`, `ui/chat/ReplayExportSheet.kt`: clarify the next existing action in model, phone, starter, browser and export surfaces; keep safety, sign-in, network and watermark facts. Do not change provider, install, download, browser or export behavior. Fixes unexplained terms and flat loading moments.
